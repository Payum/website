## Platform

web

## Users

**Primary: a PHP developer with a checkout to build, deciding whether to adopt Payum.** They arrive comparing Payum against Omnipay, a framework-specific package (Laravel Cashier, a Symfony payment bundle), or wiring a gateway SDK such as Stripe's directly. They are usually mid-project, under delivery pressure, and the visit is short — the site has to make an adoption decision possible in one sitting, not sell a feeling.

Their real question is two-part: *does Payum cover what my payment flow actually needs* (not just "charge a card"), and *is this project alive enough to depend on*. Both must be answerable without leaving the page.

Secondary audiences exist — existing users hunting a doc, leads vetting a dependency, contributors and gateway authors — but no surface should be designed for them at the primary user's expense.

## Product Purpose

Payum is a payment processing library for PHP. It gives an application one interface — one set of request objects and one payment model — for working with 50+ payment processors, so that adding, swapping or supporting multiple gateways does not mean rewriting checkout code against each processor's own SDK and redirect dance.

Success is a developer shipping a working, correct payment flow — including the parts that are usually left as an exercise: the redirect handshake, gateway notifications, and knowing with certainty what state a payment is in.

## Positioning

Three claims a neighbouring PHP payment library could not truthfully copy. Confirmed with the maintainer; these are the load-bearing arguments for the whole site.

1. **The full payment lifecycle is first-class, not just the charge.** Capture, Authorize, Refund, Cancel, Payout, Sync, GetStatus and recurring agreements are all modelled as request objects. Competing wrappers typically cover the charge well and hand the rest back to the developer.
2. **Payum owns the security-token and storage model.** Single-purpose tokens carry the gateway, the payment model and the after-url, so payment details never ride in URLs; storage is an interface (Doctrine ORM, MongoDB, filesystem, or the developer's own), never an imposed schema.
3. **A framework-agnostic core with real, maintained bridges.** Plain PHP at the bottom, thin bundles above for Symfony, Laravel and Laminas. Payment code survives a framework migration.

A fourth architectural property — every step is a replaceable action, and every request passes through extensions (logging, retries, FX, fraud checks) — is true and valuable, but the maintainer did not mark it as a differentiating claim. Treat it as a capability to explain, not a headline to lead with.

## Operating Context

- **This repository is the marketing site only** (`payum.dev`). Reference documentation lives on a separate property, `https://docs.payum.dev/`, generated by GitBook from `docs/` in the library repository — so a live URL mirrors its file path, and `docs/SUMMARY.md` is the authoritative table of contents. Verified 200 as of 2026-08-18: `/get-it-started`, `/payum-vs-omnipay`, `/supported-gateways`, `/frameworks-and-e-commerce-integration`, `/storages`, `/instant-payment-notification`. **`/get-it-started` is the first-hour path** and is the correct destination for a "read the docs" action; the bare root is not. The 2.0 documentation is a parallel tree under `/v2` (see Capabilities) — unprefixed `/gateways` and `/di` are 404 because those pages exist only under `/v2`.
- **The library is `Payum/Payum` on GitHub**, distributed via Composer/Packagist as `payum/payum` (`composer require payum/payum`). Framework bridges are separate packages: `payum/payum-bundle` (Symfony), `payum/payum-laravel-package`, `payum/payum-module` (Laminas).
- The evaluating developer's scene is a terminal, a `composer.json`, and an existing framework app. Code the visitor could paste is the most persuasive material the site has; screenshots of a UI are not, because Payum has no UI.
- Legacy footprint: the library's own `composer.json` still lists `payum.forma-pro.com` as its homepage. The new site does not have to honour that URL, but it should expect inbound visitors who know the project by the old one.

## Capabilities and Constraints

- 50+ payment processors, spanning card gateways (Stripe, Adyen, Braintree, Authorize.Net, Worldpay), wallets and local methods (PayPal, Klarna, Sofort, Alipay, WeChat Pay, Przelewy24, SEPA Direct Debit), crypto (Coinbase, BitPay), and offline/custom gateways.
- Payment state is a fixed, documented vocabulary: `STATUS_NEW`, `STATUS_PENDING`, `STATUS_AUTHORIZED`, `STATUS_CAPTURED`, `STATUS_REFUNDED`, `STATUS_FAILED`, `STATUS_CANCELED`. This is domain language, not marketing copy — keep it verbatim wherever it appears.
- Requires **PHP ^8.1**. Licensed **MIT**. No hosted service, no account, no pricing, no dashboard: there is nothing to sign up for and no logged-in state to design.
- Current released line is **1.7.x**. 1.7.7 was tagged **2025-12-24**, while commits land weekly (most recent 2026-08-17). That gap is a product fact, not a discrepancy: framing liveness on release date alone understates the project, and framing it on commit activity alone overstates release cadence.
- **2.0 is real and in active development.** Verified from the library repository: `2.x` is the **default branch** (`origin/HEAD → origin/2.x`), and `CHANGELOG.md` carries a substantial `## 2.0.0 (TBD)` section. Confirmed 2.0 changes, from `UPGRADE.md` and the changelog:
  - PHP 7.x and Twig 1.x support dropped; Propel storage and the Guzzle bridge removed.
  - Gateways are built with a **dependency-injection container** (php-di); a factory implements `Payum\Core\DI\ContainerConfiguration`. The old `GatewayFactoryInterface::create()` path still works but deprecates.
  - The HTTP client is now **PSR-18**; `HttplugClient` is deprecated and slated for removal in 3.0.
  - **Gateway-supplied templates**: a handler can return `RenderTemplate` and `Payum::capture()` renders it, so a gateway ships a card form or wallet button without the application writing rendering code.
  - `StatusAwareInterface` keeps a subject's status current after every command.
  - `Result::$status` is null when an operation concluded nothing, so a declined refund no longer reads as a failed payment.
  - The `Payum\Core\Bridge\Symfony` namespace is deprecated in favour of `payum/payum-bundle`.

- **2.0 documentation is published but incomplete.** It lives under the `/v2` prefix — `https://docs.payum.dev/v2` — and **not all pages have been updated for 2.0 yet, so the v2 tree cannot be taken as-is**. The pages confirmed by the maintainer to reflect how 2.0 actually works, and therefore the only ones safe to rely on:
  - `https://docs.payum.dev/v2/the-architecture`
  - `https://docs.payum.dev/v2/gateways` and everything beneath it
  - `https://docs.payum.dev/v2/di` and everything beneath it

- **Decision (2026-08-18): 2.0 stays off this site for now.** There is significant work left, the changelog carries no date, and much of the v2 doc tree is still 1.x content. Do not announce, describe, date or link 2.0 from any surface until the maintainer reopens this.

- **A full site redesign is planned for the 2.0 launch**, to match 2.0's new structure. This is durable context for anything built here now: **the current site is an explicitly interim artifact.** Weigh structural investment accordingly — quality that ships today (accessibility, correctness, copy that is true) still earns its keep, but large restructuring of information architecture will be superseded and should not be undertaken on the assumption it is permanent.

## Brand Commitments

- The name is **Payum**, always capitalised exactly so, as a plain word — no all-caps, no stylised spelling. The current mark is a small accent square plus the wordmark.
- **MIT / open source is part of the identity, not a footnote.** "No vendor lock-in" is a claim the project can make and means.
- Voice is that of a maintainer talking to a peer: precise, domain-fluent, unhyped. The existing copy sets the bar ("Funds reserved, capture when you ship") — real payment vocabulary beats adjectives. Never let generated copy soften it into generic SaaS marketing.
- The dark crimson-on-near-black visual world already implemented is design authority, recorded separately; it is not re-litigated here.

## Evidence on Hand

Real, and cleared for use. Figures re-verified against Packagist and the library repository on **2026-08-18** and unchanged within their rounding — the round-down convention below is holding.

- **Downloads:** 6.83M total, ~41k/month on Packagist for `payum/payum`.
- **GitHub:** ~1,924 stars, ~347 forks on `Payum/Payum`.
- **Liveness:** released 1.7.7 (tagged 2025-12-24) with commits landing weekly. Both halves are needed — see Capabilities.

- **Verified lifecycle code exists and may be shown.** The site currently proves only *configuration*; nothing on it shows a request executing, which leaves the first positioning claim asserted rather than demonstrated. The canonical calls live in the library's own `docs/get-it-started.md` and are **identical on the released 1.7.x line and on 2.x**, so they are safe to publish:
  - `$gateway->execute(new Capture($token), true)`, whose reply is checked for `HttpRedirect` / `HttpPostRedirect`.
  - `$gateway->execute($status = new GetHumanStatus($token));` then `$status->getValue()`.
  Source these from the repository rather than composing them.

- **A first-party Omnipay comparison exists**: `docs/payum-vs-omnipay.md`, published at `https://docs.payum.dev/payum-vs-omnipay`. It is the project's own document, so its claims are quotable without inventing anything. Its substantive points: swapping Stripe for PayPal in Omnipay forces application changes because the two require different data (a card versus return/cancel URLs) while Payum hides that inside the gateway; Payum generates the secure return and notify URLs and invalidates them once spent; and Omnipay exposes only success/failed where Payum carries a fuller status set. This resolves the standing gap where the site never acknowledges an alternative.
- **Support window:** PHP ^8.1+, MIT licence — both quotable as-is.
- **Adopters are ecosystem packages, not end-user companies.** Cleared to name: **Sylius** (`sylius/core`, `sylius/payum-bundle`) and **CoreShop** (`coreshop/core-shop`, `coreshop/payum-bundle`), plus the third-party Sylius gateway plugin ecosystem (Setono, Webgriffe, Locastic). 25 packages depend on `payum/payum` on Packagist. Verified against Packagist's dependents list.
- **Not available — do not fabricate:** no named end-user companies, no customer logos, no testimonials, no quotes, no case studies, no uptime/performance benchmarks, no revenue-processed figure, and **no 2.0 release date**. If a surface needs social proof beyond the numbers above, ask; do not invent a logo wall.

## Product Principles

1. **Answer the adoption question, don't decorate it.** Every surface earns its place by moving a comparing developer toward a decision — coverage, correctness, liveness — not by adding atmosphere.
2. **Code is the product's imagery.** Payum has no UI to show. Real, runnable, framework-specific PHP is the most persuasive asset available and should be treated as a primary visual element rather than a supporting detail.
3. **Speak the payment domain exactly.** Real verbs and real status constants over invented marketing vocabulary. Precision is the credibility signal for this audience.
4. **Prove liveness with facts.** For an OSS dependency, "is this maintained?" is the silent objection. Downloads, stars, release version and PHP support window are on hand — use them rather than adjectives.
5. **Claim only what is verified.** The project's honesty is part of its pitch. Numbers get re-checked before publishing; absent proof stays absent.

## Accessibility & Inclusion

**WCAG 2.2 AA is the required standard** for this site. Contrast below 4.5:1 on body text, touch targets under 44px, missing focus states, and heading outlines that skip levels are defects, not nitpicks. A prior critique of the landing page found two AA contrast failures (an 11.5px code filename at 3.77:1, the footer licence line at 3.56:1) and undersized mobile targets — that class of issue is in scope for any work touching those surfaces.
